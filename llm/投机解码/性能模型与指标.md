# 投机解码的性能模型与指标

[[llm/投机解码/README|投机解码总览]] · 正确性基线：[[Speculative Sampling]] · 方法对照：[[Medusa]]、[[EAGLE]]、[[DSpark]]

性能问题的核心不是“draft 接受率高不高”，而是：**每次昂贵的 target verification 实际提交多少 token，是否足以摊薄 draft、验证和调度成本。**

vLLM 当前将 draft acceptance rate、mean acceptance length 和逐位置接受率作为 speculative decoding 指标公开；其定义可参见 [metrics API](https://docs.vllm.ai/en/latest/api/vllm/v1/spec_decode/metrics/) 与 [feature guide](https://docs.vllm.ai/en/latest/features/speculative-decoding/)。

## 计数口径

对固定 draft 长度 $m$ 的 $N$ 轮解码，记：

- $D=Nm$：总 draft token 数；树形候选应改为“实际送入 target 验证的候选节点数”。
- $A$：被 target 接受的 draft token 数；**不含**拒绝位置由 target 补出的 token，也不含 all-accepted 时的 bonus token。
- $L_j$：第 $j$ 轮实际提交的 token 数。标准 linear speculative sampling 中，若未遇 EOS，$L_j=1+a_j$，其中 $a_j$ 是该轮已接受的 draft token 数；额外的 $1$ 就是 rejection token 或 bonus token。

| 指标 | 定义 | 用途与陷阱 |
| --- | --- | --- |
| Draft acceptance rate | $A/D$ | 衡量 proposal token 的平均质量；长度不同的配置不可只用它比较 |
| Mean accepted draft length | $A/N$ | 一轮平均接收多少 proposal token |
| Mean acceptance length | $\bar L=\frac1N\sum_jL_j=1+A/N$ | 更接近能摊薄 target 调用的实际收益；vLLM 的惯例包含 bonus / rejection token |
| Per-position acceptance $r_i$ | $r_i=\Pr(a_j\ge i)$ | 看第几步开始明显失准，决定是否应缩短 draft length 或树深 |
| Accepted throughput | 已提交 token / 秒 | 最终服务吞吐指标；需与 baseline 同设置对比 |
| TPOT / ITL | 解码阶段的每输出 token 时间 / 相邻输出间隔 | 面向流式体验；应报告均值及 p50/p95 |
| TTFT | 从请求到首 token 的时间 | 通常主要受 prefill 与排队影响，不能用它替代 decode speedup |

注意：有的系统把“每个位置接受率”记为第 $i$ 个 token 被接受的比例，等价于上面的 $r_i$；它不是条件概率 $\Pr(\text{第 }i\text{ 个接受}\mid\text{前 }i-1\text{ 个接受})$。报告时应注明口径。

## 从接受率到期望提交长度

按上面的逐位置定义，单轮期望接受 draft token 数为

$$\mathbb E[a]=\sum_{i=1}^{m}r_i.$$

忽略 EOS 时，标准线性 speculative sampling 的期望提交长度为

$$\mathbb E[L]=1+\sum_{i=1}^{m}r_i.$$

如果粗略假设每个位置在此前都通过时，以相同概率 $\rho$ 继续接受，那么 $r_i\approx\rho^i$，于是

$$\mathbb E[L]\approx1+\rho+\rho^2+\cdots+\rho^m.$$

这个近似的价值是直觉而非拟合：即使平均 draft acceptance rate 看上去不错，后几位的接受率快速下降时，增加 $m$ 的边际收益也会很小。对 [[Medusa#Tree Attention|候选树]] 和 [[EAGLE#EAGLE2|EAGLE-2]]，应将 $r_i$ 扩展为“在给定预算下，树覆盖到可接受路径第 $i$ 个位置的概率”；不能把线性公式原样套用。

## 一个可用于比较配置的简化时间模型

设：

- $T_{\rm target}(m)$：target 对一个含 $m$ 个线性候选的 verification forward 时间；
- $T_{\rm draft}(m)$：生成这些候选的时间；
- $T_{\rm overhead}(m)$：采样、接受/残差计算、tree mask、KV cache 写回、调度等时间；
- $T_{\rm target}(1)$：不用投机时生成一个 token 的 target decode 时间。

则 speculative 的平均每 token 时间近似为

$$T_{\rm spec/token}\approx\frac{T_{\rm draft}(m)+T_{\rm target}(m)+T_{\rm overhead}(m)}{\mathbb E[L]},$$

相对于普通 decode 的近似加速比为

$$S\approx\frac{\mathbb E[L]\,T_{\rm target}(1)}{T_{\rm draft}(m)+T_{\rm target}(m)+T_{\rm overhead}(m)}.$$

只有 $S>1$ 才值得开启投机解码。这个公式也解释了两个常见现象：

- **高接受率不必然更快**：更长 draft 或更大树也会抬高 $T_{\rm draft}$、$T_{\rm target}$ 与 overhead。
- **target 的一次长验证不等于一次普通 decode**：它可能因 GEMM 批量化而更划算，也可能受长上下文 attention、tree node 数和 KV cache 带宽影响而变贵；必须实测 wall-clock。

树形方法可把 $m$ 替换为 verification node budget $B$，并把 $T_{\rm target}(m)$ 写成 $T_{\rm target}(B)$。此时“接受率”之外还要报告节点利用率与实际提交长度，否则不同树宽 / 树深不可比较。

## 最小观测集

每个实验至少同时记录 baseline 与 speculative 的下列量，并固定模型、硬件、并发度、请求长度分布、采样参数和输出约束：

1. 请求数、输入 / 输出 token 数、并发度和上下文长度分位数；
2. $m$（或 tree node budget）、$A$、$D$、$N$、$\bar L$、逐位置 $r_i$；
3. accepted throughput、draft throughput、target-only throughput；
4. TTFT、TPOT / ITL、端到端 latency 的 mean、p50、p95；
5. target、draft、overhead 三段的 wall-clock，以及 GPU memory / KV cache 使用量。

这样才可以回答“该调大 draft length 吗”：若末端 $r_i$ 很低且验证成本上升，就缩短；若 $r_i$ 仍高且 target verification 可有效并行，则可以增加长度。对于 [[DSpark#设计|DSpark]] 这类按置信度或负载调度的方法，还应按负载桶分别汇报，不能只给全局平均值。
