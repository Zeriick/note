# 结构化并发

结构化并发（structured concurrency）要求：在一个并发作用域中创建的子任务，必须在离开该作用域前完成、失败或被取消。父作用域拥有子任务，并负责统一等待、取消、收集错误和清理资源。

```text
task scope
├── child A
├── child B
└── join / cancel / propagate failure
```

父子任务因而形成一棵生命周期树：

- 子任务不能悄悄活过父作用域，成为无人管理的 orphan task。
- 子任务失败必须被父作用域观察，通常会触发兄弟任务取消和错误向外传播。
- 父作用域退出时，可以确定内部并发活动已经收束。
- 资源生命周期可以覆盖所有使用资源的子任务。

非结构化写法常见于启动裸线程、提交任务后丢弃 future，或把 task handle 传出创建作用域：

```text
parent: ├──────────────┤
child:      ├────────────────────────┤
                         ^ parent 已结束
```

此时很难局部回答：谁等待、谁取消、错误交给谁，以及资源何时可以释放。

## 和结构化控制流的联系

结构化控制流用 `if`、`while`、函数等单入口、受控出口的区域约束任意 `goto`；结构化并发用 task scope 约束任意任务创建、等待和逃逸。二者都把一般图尽量组织成可嵌套的树，从而支持局部推理。

可以做一个非严格类比：

| 结构化控制流 | 结构化并发 |
|---|---|
| loop / region | task scope |
| 唯一 header | 明确的父作用域 |
| 支配区域内部 | 父作用域拥有子任务生命周期 |
| 统一退出/cleanup | join、cancel、错误收束 |
| 跳入循环内部 | 外部越过 scope 介入内部任务 |
| 跳过清理而离开 | 子任务逃逸并活过父 scope |

从 dominance 的角度联想：进入 scope 类似“支配”子任务的产生；join/cancel/cleanup 类似子任务生命周期到父作用域出口之间必须经过的 post-dominator。它不是结构化并发的正式定义，但能说明结构边界为什么有利于资源和错误管理。

## 和 reducible CFG 的区别

两者不能直接画等号：

- reducible / irreducible 是静态 CFG 上关于 SCC、入口和支配关系的图论性质。
- structured / unstructured concurrency 是动态任务实例的生命周期、所有权和失败传播性质。
- 一个函数可以有很规整的 CFG，却启动 detached task 后直接返回，此时并发仍不结构化。
- 一个结构化异步函数降低成状态机后 CFG 可能很复杂，甚至需要特殊处理，但高级任务生命周期仍然可以是结构化的。

因此它们是两个正交维度，共享的是“不要随意绕过结构边界”的设计哲学。

编译器里的具体联系见 [[complier/Jump Threading#Reducible 与 irreducible 风险|Jump Threading：reducible 与 irreducible 风险]]。

## 一句话总结

结构化控制流规定“控制怎样进入和离开代码区域”；结构化并发规定“任务归谁所有、活到什么时候、如何统一结束”。两者都用明确的嵌套边界换取可组合性、局部推理和可靠清理。
