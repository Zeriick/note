# SSA：静态单赋值形式与构造

SSA（Static Single Assignment，静态单赋值）是一种中间表示形式：每个 SSA value 只有一个静态定义，使用者可以通过 def-use 链直接找到它的定义。“单赋值”限制的是 IR value 的定义次数，不是说运行时的内存位置只能被写一次。

## 为什么使用 SSA

在非 SSA 形式中，同一个变量可能被多次赋值，某次使用到底来自哪个定义需要额外的 reaching-definitions 分析。SSA 通过重命名把不同定义变成不同值：

```text
x = 1          x1 = 1
x = x + 1  =>  x2 = x1 + 1
use(x)          use(x2)
```

因此，常量传播、死代码删除和范围分析等优化可以沿真实的 def-use 依赖工作，而不必反复扫描所有指令。

## 合流与 φ 节点

当 [[dom|CFG]] 中多条路径在一个 basic block 合流，且各路径带来不同定义时，使用 Phi 节点按实际到达的 predecessor 选择值：

```text
entry:
  if c goto left else right
left:                 right:
  x1 = 1                x2 = 2
  goto join             goto join
join:
  x3 = phi [left: x1], [right: x2]
  use(x3)
```

Phi 不是“同时计算两个值”；它根据控制流的来边选择对应输入。因此，改写 CFG 时必须同步增删或转译 Phi 输入。

## 构造要点

经典构造过程包括：

1. 计算 dominator tree 和 dominance frontier。
2. 对每个有多个可能到达定义的合流区域放置 φ。最小 SSA 只放置语义所需的 φ；pruned SSA 还会利用活跃性避免为不再使用的变量放置 φ。
3. 沿 dominator tree 重命名，使每个使用都指向支配它的唯一定义。

正确性的核心不变式是：除 φ 的边上使用等特殊规则外，每个 SSA 定义都必须支配它的所有使用。

## 从内存形式提升到 SSA

一种常见构造入口是 Mem2Reg：局部变量先表示为 `alloca/load/store`，再提升成 SSA value。

```text
p = alloca i32
store 0, p
if c:
    store 1, p
x = load p
```

提升后不再需要 `p` 对应的真实内存读写，而是使用版本化 value 和 Phi。

一个对象通常只有在满足下列条件时才可提升：

- 表示单个可分离的标量；
- 地址不逃逸；
- 所有使用都是可理解的直接 load/store；
- 没有 volatile、atomic 或其他必须保留真实内存可观察性的语义；
- 访问类型与对象类型一致。

聚合对象往往需要先经过 Scalar Replacement of Aggregates（SROA，聚合标量替换），拆成可独立提升的标量。

## Phi 放置算法

对每个待提升变量 `x`，先收集所有定义块 `DefBlocks(x)`，再计算 iterated dominance frontier：

```text
worklist = DefBlocks(x)
while worklist 非空:
    D = pop(worklist)
    for Y in DF(D):
        if Y 尚未为 x 放置 Phi:
            在 Y 放置 Phi(x)
            push(Y)
```

新放置的 Phi 还要进入 worklist，因为 Phi 自己也是 `x` 的新定义，它可能在更远的汇合点与其他定义再次合流。

### Minimal、Pruned 与 Semi-pruned SSA

只使用 IDF 会得到接近 minimal SSA 的结果，但仍可能产生结果从未被使用的 Phi。

Pruned SSA 额外要求变量在候选块 live-in：

```text
Y in IDF(DefBlocks(x))
并且 x live-in at Y
    => 在 Y 放 Phi
```

Semi-pruned SSA 使用较便宜的活跃性近似，构造成本与精度介于未剪枝和完整 pruned SSA 之间。

## 沿支配树重命名

放置 Phi 后，为每个源变量维护一个 value stack，并沿 dominator tree 深度优先遍历：

```text
rename(block B):
    记录本块对每个变量 push 了多少次

    for phi in B.phis:
        push(phi.result 对应的变量)

    for inst in B 的普通指令:
        if inst 是 load x:
            用 stack[x].top 替换 load 结果
        if inst 是 store v -> x:
            push v 到 stack[x]

    for successor S of B:
        for S 中关于 x 的 Phi:
            给边 B -> S 添加 stack[x].top

    for child in dominatorTree.children(B):
        rename(child)

    撤销本块进行的所有 push
```

沿支配树而非普通 CFG 遍历，是为了让栈顶始终表示当前区域最近的支配定义；离开子树时 pop，兄弟区域便不会错误看到该定义。

### 未初始化路径

如果某条路径可能先读后写，必须由语言或 IR 明确处理：产生 `undef`、拒绝该程序、插入语言规定的默认值，或不进行提升。不能在没有语义依据时擅自使用 0。

## 循环中的 SSA

归纳变量是 Phi 的典型用途：

```text
preheader:
    i.start = 0
    jump header

header:
    i = phi [i.start, preheader], [i.next, latch]
    ...

latch:
    i.next = i + 1
    branch ..., header, exit
```

Phi 同时接收循环外初值和回边 recurrence value。这种结构是 [[SCEV]] 中 `AddRec {start,+,step}` 的主要来源。

## Phi/Upsilon：一种边显式化表示

传统表示把 incoming pair 放在 Phi 中：

```text
merge:
    x = phi [a, left], [b, right]
```

另一种实现会把 incoming value 显式放到 predecessor edge：

```text
left:
    upsilon x.phi, a
    jump merge

right:
    upsilon x.phi, b
    jump merge

merge:
    x = phi
```

这种表示强调“Phi incoming 是边上的数据”，但它只是 IR 设计变体，不是 SSA 的普遍定义。两种表示都必须保证每条 predecessor edge 为每个 Phi 提供且只提供一个正确 incoming value。

## Critical Edge

边 `P -> S` 在 `P` 有多个 successors、且 `S` 有多个 predecessors 时是 critical edge。

如果需要在这条边上插入只属于该边的 copy，既不能放在 `P` 尾部，也不能直接放在 `S` 开头，通常要拆边：

```text
P -> S
```

变成：

```text
P -> Split -> S
```

原本属于 `P -> S` 的 Phi incoming 也要迁移为来自 `Split -> S`。寄存器分配阶段消除 Phi 时尤其常见，详见 [[寄存器分配]]。

## CFG 改写中的 SSA 维护

### 删除入边

同步删除 successor 中每个 Phi 对应的 incoming。Phi 若退化为唯一 incoming，通常可继续折叠。

### 新增入边

必须为 successor 中的每个 Phi 构造新 incoming，而且该 value 要在新边上可用。

### 重定向边

同时包含“从旧 successor 删除 incoming”和“为新 successor 添加 incoming”。如果新 incoming 依赖被绕过块中的计算，还需证明可以代入、复制或重算。

### 复制区域

建立 old value → cloned value 映射，重写复制区域内 operands、边 targets 和边界 Phi。

这也是 [[Jump Threading]]、tail duplication、loop peeling 和 unrolling 的主要实现难点。

## LCSSA

Loop-Closed SSA（LCSSA）要求循环内定义、循环外使用的 value 先经过 exit Phi：

```text
loop body:
    v = ...

exit:
    v.out = phi [v, exiting-edge]

after:
    use(v.out)
```

LCSSA 并没有让程序“更 SSA”；它额外约束循环边界，使循环变换只需集中处理 exit values。详见 [[循环规范形与 LCSSA]]。

## SSA 消除

机器指令通常不直接执行 Phi。SSA destruction 为每条入边生成平行复制：

```text
x = phi [a, P1], [b, P2]
```

转为概念上的：

```text
P1 -> B edge: x <- a
P2 -> B edge: x <- b
```

这些 copy 必须按 parallel-copy 语义解析。例如 `r1 <- r2; r2 <- r1` 不能顺序执行，需要临时位置打破环。Phi elimination、copy coalescing 与 [[寄存器分配]] 因而紧密相关。

## SSA 与 PAG

[[PAG|Pointer Assignment Graph（PAG）]] 常把 pointer-typed SSA values 当作节点，copy 和 φ 会产生指针值传播约束。SSA 的唯一定义和 def-use 链使这些边容易构造与稀疏遍历。

但两者不是同一张图：SSA def-use 图表示 IR values 的定义与使用；PAG 还要显式表示 abstract memory objects，并为 address/copy/load/store/field 等操作建立不同约束。标量 SSA 不会自动区分两个 pointers 是否指向同一内存位置；这是 points-to/alias analysis 需要解决的问题。

MemorySSA 则是另一种针对内存访问版本和 clobber 关系的 SSA-like 表示，也不等同于 PAG。它通常需要 [[内存优化证明：Alias Analysis 与 MemorySSA|Alias Analysis]] 帮助判断哪些写可能影响某次读。

## 正确性边界与常见错误

- 不可达块、异常边和多重边会影响 Phi 的放置和输入语义。
- Phi operand 是 edge use，不能按普通块内 use 处理。
- 只计算一阶 dominance frontier 会漏掉由新 Phi 引出的更远汇合点。
- rename 应沿 dominator tree，而不是随意沿 CFG 遍历。
- 离开支配树子树时必须恢复 value stack。
- 新增、删除或重定向 edge 时，Phi incoming 必须同步变化。
- SSA 重命名消除的是标量名称上的多次定义，不是通过指针发生的内存别名。
- 普通 SSA 不自动满足 LCSSA；循环改写可能重新产生直接 loop-outside use。
