# 循环依赖分析

循环依赖分析回答：不同迭代中的内存访问是否必须保持某种先后顺序。它是并行化、向量化、loop interchange、fusion、fission、tiling 和软件流水等变换的合法性基础。

分析的核心不是“两个表达式长得像不像”，而是求解：是否存在两个合法迭代，使两次访问的字节区间重叠，并且至少有一次是写。

## 1. Source、Sink 与依赖种类

按原程序执行顺序，较早访问称为 source，较晚访问称为 sink。

### Flow / True Dependence（RAW）

Read After Write：sink 读取 source 写入的值。

```c
store A[k] = v;
x = load A[k];
```

这是实际数据流，通常最难消除。

### Anti Dependence（WAR）

Write After Read：sink 写入 source 之前读取的位置。

```c
x = load A[k];
store A[k] = v;
```

它来自存储位置复用，有时可通过重命名、privatization 或 expansion 消除。

### Output Dependence（WAW）

Write After Write：两次写入同一位置，最终可见值取决于顺序。

```c
store A[k] = v1;
store A[k] = v2;
```

### Input Dependence（RAR）

Read After Read 通常不限制重排，因为两次都不修改内存。它可能影响缓存性能，但不是普通的数据正确性依赖。

## 2. Loop-Independent 与 Loop-Carried

### Loop-Independent Dependence

source 与 sink 在同一次迭代中发生：

```text
i_source = i_sink
```

### Loop-Carried Dependence

source 与 sink 位于不同迭代：

```text
i_source != i_sink
```

例如：

```c
for (int i = 1; i < n; ++i)
    A[i] = A[i - 1] + 1;
```

迭代 `i-1` 对 `A[i-1]` 的写，被迭代 `i` 读取，形成距离为 1 的 loop-carried flow dependence。这通常阻止各迭代任意并行执行。

## 3. Direction 与 Distance

对一层循环，依赖方向常表示为：

- `<`：source iteration 在 sink iteration 之前；
- `=`：同一迭代；
- `>`：source iteration 在 sink iteration 之后。

也可写成 `Forward / Same / Backward`，方向命名必须明确采用的是 source-to-sink 还是 sink-minus-source 约定。

若能得到精确差值，可记录 dependence distance：

$$
d = i_{sink} - i_{source}.
$$

在前面的 recurrence 中，`d = 1`。

Distance 比 direction 更强：`d=1` 蕴含正向依赖，但方向 `<` 不说明相距多少次迭代。

## 4. 嵌套循环与 Direction Vector

对嵌套循环：

```c
for (i = ...)
  for (j = ...)
    ...
```

依赖方向写成向量：

```text
(direction_i, direction_j)
```

例如 `(=,<)` 表示 source 与 sink 位于同一个 `i` 迭代，但 source 的 `j` 迭代更早。

合法执行顺序通常要求 direction vector 的第一个非 `=` 分量与原字典序一致。Loop interchange 会交换向量维度，因此必须重新检查第一个非 `=` 分量是否合法。

## 5. 先做 Object 与 Alias 过滤

对两次访问，首先判断 memory objects：

- 若能证明属于不同且不 alias 的对象，则无依赖；
- 若对象可能 alias，不能仅因地址公式不同就忽略；
- 若属于同一对象，再分析对象内 offset 和 access size。

Alias Analysis 只能回答对象/位置是否可能重叠，不能独立回答不同迭代的顺序和距离。详见 [[内存优化证明：Alias Analysis 与 MemorySSA]]。

## 6. 仿射地址表示

循环访问常规范化为对象相对 byte address：

$$
Addr(\vec{i}) = Base + c_0 + \sum_k c_k i_k.
$$

其中：

- `Base` 是 memory object；
- `c0` 是 loop-invariant offset；
- `ck` 是对应循环维度的 byte stride；
- `ik` 是迭代变量。

单次访问还需要 `access size`。两次起始地址不同也可能因访问宽度而重叠：

```text
[addr1, addr1 + size1)
[addr2, addr2 + size2)
```

## 7. 依赖方程

对 source 和 sink：

$$
Addr_s(\vec{i}) = Addr_t(\vec{j})
$$

是标量单字节访问的基本方程。考虑访问宽度后，需要判断两个半开区间是否重叠。

单循环、等步长情况下：

$$
b_s + s i = b_t + s j.
$$

于是：

$$
s(j-i)=b_s-b_t.
$$

若差值不能被步长整除，则不存在精确同址迭代；若可整除，可以得到候选 distance，再检查迭代范围和原程序执行顺序。

## 8. GCD Test

对线性丢番图方程：

$$
a i - b j = c,
$$

存在整数解的必要条件是：

$$
\gcd(a,b) \mid c.
$$

若不整除，可以证明无依赖；若整除，只表示存在整数解，还需要检查：

- `i`、`j` 是否落在合法迭代域；
- source 是否在原执行顺序中早于 sink；
- access size 是否造成额外重叠；
- 外层循环上下文是否一致。

因此 GCD test 是快速排除手段，不是完整依赖判定。

## 9. Banerjee 与区间约束

Banerjee-style test 利用循环变量上下界，估计线性地址差值的最小和最大范围。如果 0 不在可能范围中，可以证明无依赖。

它通常比纯 GCD test 更精确，但仍可能返回“可能有依赖”。更精确的方法包括：

- Delta test；
- Omega test；
- integer linear programming；
- polyhedral dependence analysis。

精度越高，构建和求解成本通常越高。

## 10. Trip Count 与迭代域

即使地址方程有整数解，该解也可能不在实际迭代范围内。例如：

```c
for (i = 0; i < 4; ++i)
    A[i] = A[i + 100];
```

形式上两个地址序列可能在更大整数域相交，但在 `i in [0,4)` 内并不相交。

因此依赖分析需要 [[SCEV]] 或其他循环边界信息提供：

- 初值；
- step；
- trip count；
- 符号 bound；
- zero-trip 条件；
- overflow 约束。

## 11. 非仿射访问

下面的访问不属于简单仿射形式：

```c
A[B[i]]
A[i * i]
A[hash(i)]
```

处理方式可能是：

- 返回 unknown，保守阻止变换；
- 用 range/points-to 信息排除一部分重叠；
- 运行时生成 alias/dependence check，选择 fast path；
- 使用更强的符号或 polyhedral 方法；
- 针对特定 idiom 建立专门证明。

不能因为“没有求出依赖”就当成“无依赖”。

## 12. 执行顺序与 CFG

地址相交只说明可能访问同一位置。要形成有向 dependence，还需要确定 source 与 sink 的执行顺序。

同一次迭代中，若两次访问位于不同 blocks，需要考虑：

- dominance；
- mutually exclusive branches；
- 多条路径是否都会执行；
- zero-trip 和 early exit；
- call 或异常边。

因此“地址依赖”和“执行顺序”最好作为两个明确步骤，而不是根据 basic block 列表顺序猜测。

## 13. 变换合法性

### Parallelization / Vectorization

若存在未消除的 loop-carried flow dependence，迭代通常不能任意并行。距离已知时，某些 recurrence 仍可通过 scan、prefix 算法或专门 vector idiom 处理。

### Loop Interchange

交换循环层次会交换 direction vector 的维度。变换后不能让第一个非 `=` 方向与新执行字典序冲突。

### Loop Fusion

融合改变两个循环 body 的交错顺序。需检查跨循环 flow/anti/output dependences，以及两个迭代域是否对齐。

### Loop Fission

拆分会把原本同一迭代内的语句分到两个循环，可能把 loop-independent dependence 变成跨整个循环的顺序要求。

### Tiling

Tiling 改变迭代遍历顺序。只有当 tile schedule 保持所有必要 dependence 的方向时才合法。

### Loop-Carried Forwarding

如果能证明固定距离，例如 store 在迭代 `i-1` 写入、load 在迭代 `i` 读取，可以把内存 recurrence 转成 scalar Phi recurrence。这是消除特定 loop-carried memory dependence 的一种方式。

## 14. NoDependence、Dependence 与 Unknown

一个健壮的接口应区分：

- `NoDependence`：已经证明不存在相关依赖；
- `Dependence`：已经证明可能/必然存在，并可附带 kind、direction、distance；
- `Unknown(reason)`：当前方法无法得出足够强结论。

常见 unknown 原因：

- 两个对象可能 alias；
- 地址不是仿射形式；
- stride 或 offset 差不是常量；
- trip count 未知；
- nested-loop variation 超出模型；
- 求解空间过大；
- 算术可能溢出。

保留 reason 能区分“真实存在依赖”和“分析能力不足”。

## 15. 常见误区

- 两个 pointer values 不同就认为无依赖。
- 只比较数组下标表达式，不考虑 base object。
- 忽略 access size 和 partial overlap。
- 地址方程有整数解，就认为合法迭代域中一定有解。
- GCD 整除就断言存在依赖。
- 忽略 source/sink 的原执行顺序。
- 只分析内层循环，遗漏外层 context strides。
- 把 unknown 当成 `NoDependence`。
- 看到固定 distance 就直接向量化，没有检查 dependence kind 和方向。
