# 计算原语与归约

Tile primitive 表达一块数据上的整体操作。它描述“做什么”，后端再根据 scope、shape、dtype、layout 和 target 选择“怎么做”。

## Primitive 与指令

```text
TileLang primitive
  -> layout / shape / target constraints
  -> target-specific implementation
  -> one or more GPU instructions
```

因此：

- `T.copy` 不固定等于普通 load/store，也可能降低为向量化 copy、异步 copy 或目标相关搬运；
- `T.gemm` 不固定等于某一条 MMA 指令，它还包含 tile 分解和 fragment 约束；
- reduction 可能包含线程内累加、warp shuffle、shared partial 和同步。

Primitive 的价值在于复用一套经过验证的 lowering，同时保留与手写 `T.Parallel` 混合的能力。

## 常见原语

| 原语 | 语义 |
| --- | --- |
| `T.copy(src, dst)` | 在不同 buffer/scope 间搬运 tile |
| `T.clear(buf)` / `T.fill(buf, x)` | 初始化 tile |
| `T.gemm(A, B, C)` | tile GEMM，累加到 `C` |
| `T.reduce_*` | 对 buffer 指定维度做整体 reduction |
| `T.alloc_reducer` | 创建可在 `T.Parallel` 中增量更新的 reducer |

选择整体 primitive 还是显式循环：

```text
规则、可复用的核心路径 -> primitive
不规则融合、特殊边界   -> T.Parallel / control flow
```

## `T.copy`

```python
T.copy(A[by * BM, ko * BK], A_shared)
T.copy(C_local, C[by * BM, bx * BN])
```

降低时主要观察：

- source 和 destination scope；
- tile shape 和元素类型；
- alignment 与连续维度；
- global access 是否 coalesced；
- shared layout 是否适合目标 consumer；
- copy 是否处于 pipeline 中。

Copy layout 和 compute layout 可以不同。常见路径是先以合并方式把 global tile 搬到 shared，再通过 shared layout 为 MMA 或其他消费者重排。

## `T.gemm`

```python
T.gemm(A_shared, B_shared, C_local)
```

逻辑语义为：

$$
C_{local} \mathrel{+}= A_{shared}B_{shared}.
$$

通常要求：

- `C_local` 已清零或保存前序累加结果；
- `A_shared`、`B_shared` 已填入当前 $K$ tile；
- dtype 和 shape 能匹配目标实现；
- fragment/shared layout 与所选 MMA 路径兼容。

GEMM 的数学分块、数据复用和算术强度见 [[../GEMM|GEMM 优化]]；这里关注它如何通过 TileLang 表达。

## 两种 Reduction 写法

一种是使用整体 reduce primitive：

```text
input fragment/buffer
  -> T.reduce_sum / T.reduce_max / ...
output fragment/buffer
```

另一种是使用 reducer buffer，在 `T.Parallel` 中显式累计：

```python
out = T.alloc_reducer((BM,), "float32", op="sum", replication="all")
T.clear(out)

for i, j in T.Parallel(BM, BN):
    out[i] += x[i, j]

T.finalize_reducer(out)
```

后者适合 reduction 与 elementwise 或复杂索引融合的场景。

## Reducer 生命周期

Reducer 需要明确经过四步：

```text
allocate
  -> fill/clear with identity
  -> update inside parallel region
  -> finalize
  -> consume/store final result
```

以 sum 为例：

```python
total = T.alloc_reducer((1,), "float32", op="sum", replication="all")
T.clear(total)

for i in T.Parallel(N):
    total[0] += x[i]

T.finalize_reducer(total)
```

`T.finalize_reducer` 之前，各线程可能只有 partial result；不能提前把 reducer 当成完整结果使用。

## 单位元与更新形式

Reducer 的初始化与更新必须符合 `op`：

| `op` | 初始化 | 更新 |
| --- | --- | --- |
| `sum` | `0` | `r[...] += value` |
| `max` | 足够小的值 | `r[...] = T.max(r[...], value)` |
| `min` | 足够大的值 | `r[...] = T.min(r[...], value)` |

错误单位元会产生数学错误；错误更新形式还可能破坏 compiler 对 reducer 的识别。

## `replication="all"`

Reduction 中必须区分 partial result 与最终结果的 ownership。

假设 4 个线程分别有 partial：

```text
thread 0: 1
thread 1: 2
thread 2: 3
thread 3: 4
```

最终 sum 为 10。非复制结果可以只有选定 owner 持有：

```text
thread 0: 10
others  : no final ownership
```

`replication="all"` 表示 finalize 后，最终结果在相关线程域上 fully replicated：

```text
thread 0: 10
thread 1: 10
thread 2: 10
thread 3: 10
```

这适合后续每个 warp/thread group 都要继续消费结果的场景，例如 normalization、softmax 或 GEMV 后处理。

代价可能包括额外 shuffle/broadcast 和寄存器副本。若只有一个线程负责最终 store，不需要为了“方便”复制给全部线程。

## 与 `T.Fragment(..., replicate=R)` 的区别

```text
T.Fragment replicate
  -> 通用 layout 构造
  -> 同一逻辑 fragment 有多套 thread ownership

reducer replication="all"
  -> reducer 结果策略
  -> finalize 后完整结果复制给相关线程
```

前者可以用于任意 fragment/loop layout；后者只描述 reduction result。详细映射见 [[03-Layout与线程映射#Replication]]。

## Reduction 的性能层次

典型 lowering 路径：

```text
每线程多个输入
  -> register partial
每 warp
  -> shuffle reduction
每 CTA
  -> shared partial + barrier + final warp reduction
跨 CTA
  -> atomic 或额外 kernel
```

具体采用哪些层次取决于 reduction domain、线程 layout 和输出 ownership。Reduction 的 CUDA 性能模型见 [[../CUDA Reduction 优化|CUDA Reduction 优化]]。

## 检查清单

- 这个 primitive 表达的整体语义是什么？
- 输入和输出分别位于哪个 scope？
- shape、dtype、alignment 是否满足目标 lowering？
- Reducer 是否以正确单位元初始化？
- `finalize_reducer` 是否发生在第一次读取最终结果之前？
- 最终结果需要一个 owner，还是需要 `replication="all"`？
- 复制结果带来的本地消费收益是否超过 broadcast 和寄存器成本？
