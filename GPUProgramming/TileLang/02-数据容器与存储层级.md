# 数据容器与存储层级

TileLang 用逻辑 shape 描述 tile，同时显式区分 tile 放在哪个 memory scope。

## 三类常用对象

| 对象 | 典型位置 | 可见范围 | 常见用途 |
| --- | --- | --- | --- |
| `T.Tensor` 参数 | global memory | device/kernel | 输入和输出 |
| `T.alloc_shared` | shared memory | 当前 CTA | 协作加载、跨线程复用、数据重排 |
| `T.alloc_fragment` | register-backed fragment | 逻辑上为 CTA tile，物理上分布在线程中 | 累加器、线程局部中间值 |

硬件容量、带宽和作用域见 [[../H100 Memory Hierarchy|H100 存储层次]]。

## Global Buffer

函数参数通常描述完整 global tensor：

```python
A: T.Tensor((M, K), "float16")
```

在 kernel 内使用带起点的 region 表示一个 tile：

```python
A[by * BM, ko * BK]
```

当它作为 `T.copy` 的源，而目标 shape 为 `(BM, BK)` 时，目标 shape 参与确定搬运区域。这里的表达表示 tile 起点，不应简单理解为只读取一个标量。

## Shared Buffer

```python
A_shared = T.alloc_shared((BM, BK), "float16")
```

它表示当前 CTA 可见的 shared-memory tile。典型数据路径：

```text
global tile
  -> CTA threads 协作搬运
shared tile
  -> 多次复用或供 tile primitive 消费
```

Shared buffer 的逻辑 shape 不等于物理地址布局。为了避免 bank conflict 或满足 TMA/MMA 要求，后端可能使用 swizzle 或显式 shared layout：

```text
logical coordinate -> shared-memory address
```

因此要区分：

- shape：有哪些逻辑元素；
- layout：元素如何放到 shared 地址；
- copy mapping：哪些线程搬哪些元素。

## Fragment

```python
C_local = T.alloc_fragment((BM, BN), "float32")
```

这声明了一个逻辑上形状为 `(BM, BN)` 的 fragment。它通常对应整个 CTA 的寄存器集合，而不是每个线程都分配完整的 `BM * BN` 个寄存器。

```text
logical fragment (BM, BN)
  -> layout inference / explicit Fragment layout
thread 0: local slot 0, 1, ...
thread 1: local slot 0, 1, ...
...
```

所以“CTA 共同持有 fragment”的准确含义是：

> Fragment 是 CTA 作用域中的逻辑对象；其元素按照 layout 分散到各线程的线程私有寄存器槽位。

线程之间不能像访问 shared memory 一样任意读取彼此寄存器。跨线程消费需要匹配的 primitive、shuffle、shared-memory 中转或其他 lowering。

## Shape、Layout 与 Ownership

对于 `C_local[i, j]`：

```text
(i, j)                   : 逻辑坐标
owner thread             : 哪个线程持有
thread-local slot/index  : 该线程的哪个本地位置
```

可以概括成：

```text
logical index -> (thread id, thread-local index)
```

Shape 只描述左侧的逻辑迭代域；layout 才描述右侧的物理 ownership。详细内容见 [[03-Layout与线程映射]]。

## 数据搬运

`T.copy` 表达不同 scope 之间的 tile 搬运：

```python
T.copy(A[by * BM, ko * BK], A_shared)
T.copy(C_local, C[by * BM, bx * BN])
```

概念上是：

```text
source region + destination shape/layout
  -> 一次 tile copy
  -> 合并访问、向量化或目标相关 copy lowering
```

它不是无条件对应某一条指令。具体实现取决于：

- source/destination scope；
- shape 和 dtype；
- alignment；
- layout；
- target architecture；
- 是否位于可流水化区域。

## 生命周期

| 对象 | 典型生命周期 |
| --- | --- |
| Global tensor | kernel launch 之外创建，跨 CTA 存在 |
| Shared buffer | 当前 CTA 生命周期；pipeline 时可能有多个 stage |
| Fragment | 当前 CTA 的程序作用域；其物理寄存器值属于各线程 |

Pipeline 会放大 live state：

```text
single-stage shared tile × num_stages
```

Fragment 的活跃区间过长也会提高寄存器压力，甚至产生 spill。因此声明位置、第一次写入、最后一次使用都可能影响性能。

## 初始化

累加器必须先放入正确单位元：

```python
T.clear(C_local)               # 通常清零
T.fill(fragment, value)
```

常见单位元：

| 运算 | 单位元/初始值 |
| --- | --- |
| sum / GEMM accumulator | `0` |
| max | 足够小的值 |
| min | 足够大的值 |

不能把“分配”理解为“自动初始化”。初始化是否发生、初始化成什么值，必须从接口语义或代码中明确看到。

## 检查清单

- 这个 shape 是完整 tensor、CTA tile 还是 fragment 的逻辑 shape？
- 数据实际位于 global、shared 还是 register-backed fragment？
- 哪些线程可以直接看到它？
- fragment 元素的 owner thread 和 local slot 是什么？
- shared tile 是否需要 swizzle 或 padding？
- pipeline stage 是否使 shared/register live state 超出预算？
- 使用前是否以正确单位元初始化？
